# Отчёт фронтенда для бэкенда

Дата: 21.08.2026
Проект: «База моделей» (Next.js) · API: `https://admin.agunastroy.ru/api/v1`

Ниже — всё, что мешает или ограничивает интеграцию. Отсортировано по важности.
Каждый пункт: что ожидает фронт (по макету Figma), что отдаёт API сейчас, что нужно.

## 🔴 Блокеры

### 1. CORS не пропускает фронтенд

```
OPTIONS /api/v1/site/performers
Origin: http://localhost:3131
→ 400 Bad Request
   "Disallowed CORS origin"
```

Заголовок `access-control-allow-origin` не приходит ни на preflight, ни на обычный
запрос. Браузер блокирует **все** запросы, включая публичный каталог.

**Что нужно:** добавить в `CORS_ALLOWED_ORIGINS` домены фронтенда:

```
http://localhost:3000
http://localhost:3131
https://basemodels.ru
https://www.basemodels.ru
```

**Временное решение на нашей стороне:** запросы идут через прокси Next.js
(`/api/v1/*` → `https://admin.agunastroy.ru/api/v1/*`, см. `next.config.mjs`).
Это работает, но добавляет лишний сетевой хоп и не решает проблему для
мобильного приложения / других клиентов.

## 🟠 Данные, которых не хватает в ответах

### 2. В списке каталога нет направлений работы (тегов)

`GET /site/performers` возвращает по элементу:

```
about, age, city, created_at, email, entity_type, height_cm, id, is_hidden,
likes_count, logo_url, shares_count, specialty, status, title, views_count, weight_kg
```

В макете (Figma 81:2709) на карточке сверху выводятся чипы направлений —
«Реклама +3», «Каталог», «Фото-съемки +1». Эти данные есть в детальном ответе
(`profile.work_directions`), но не в списке.

**Что нужно:** добавить `work_directions: string[]` в элементы списка
`/site/performers`. Иначе карточки каталога выглядят пустыми сверху.

Дополнительно пригодилось бы:
- `price_from` — на карточке исполнителя в списке (сейчас его нет);
- `is_favorite: bool` — чтобы сердечко показывало актуальное состояние без
  отдельного запроса избранного.

### 3. `related` в детальной анкете беднее, чем список

`GET /site/performers/{id}` → `related[]` содержит:

```
about, agency_name, city, company_name, created_at, email, entity_type, id,
is_hidden, logo_url, representative_name, specialty, status, title
```

Нет `age`, `height_cm`, `weight_kg`. Блок «Другие модели» (Figma 129:6580)
рисует те же карточки, что и каталог, — чипы «24 лет / 170 см» остаются пустыми.

**Что нужно:** отдавать в `related` ту же структуру, что и в списке каталога.

### 4. `rating_avg` всегда `null`

У исполнителя есть опубликованный отзыв (`reviews.length === 1`, `rating: 5`),
но `rating_avg: null`. В макете (Figma 343:13223) рядом с заголовком «Отзывы»
выводится средняя оценка.

**Что нужно:** считать `rating_avg` по опубликованным отзывам. То же самое для
площадок и агентств.

### 5. Нет `slug` — только UUID

Все карточки открываются по UUID: `/models/0b8cc430-7260-426d-8dbd-cc2571510371`.
Для SEO (это публичный каталог) нужны человекочитаемые адреса вида
`/models/mariya-volkova`.

**Что нужно:** добавить поле `slug` в исполнителей, площадки, проекты, агентства
и принимать его в детальных эндпоинтах наравне с UUID.

## 🟡 Фильтры и сортировка

### 6. Сортировка работает только для `popular` и `new`

Проверено: любые другие значения (`price-asc`, `rating`, `name-asc`, `bogus`)
дают один и тот же порядок — то есть просто игнорируются.

В макете в выпадающем списке «Сначала популярные» есть варианты:

| Раздел | Значения из макета |
|---|---|
| Модели | популярные · новые · возраст ↑ · возраст ↓ |
| Фотографы / Видеографы | популярные · новые · опыт ↑ · опыт ↓ |
| Площадки | популярные · новые · цена ↑ · цена ↓ |
| Проекты | популярные · новые · дата ↑ · цена ↑ · цена ↓ |
| Агентства | популярные · новые · А–Я · больше исполнителей |

**Что нужно:** поддержать эти значения в параметре `sort` (названия можно
согласовать) либо прислать список поддерживаемых, чтобы мы убрали лишние из UI.

### 7. Не хватает фильтров, которые есть в макете

`GET /site/performers` принимает: `specialty, q, city, age_min, age_max,
height_min, height_max, price_min, price_max, sort, page, page_size`.

Нет фильтров, нарисованных в панели (Figma 81:3003):

- `weight_min` / `weight_max` — «Вес»
- `gender` — «Пол»
- `experience_min` — «Опыт»
- `category` — «Категория» (fashion / коммерческая / каталог / реклама)
- `project_type` — «Тип проекта» (фото / видео / показ)
- `can_travel` — «Выезд в другие города»

`GET /site/venues` принимает: `q, city, area_min, area_max, price_min, price_max, sort`.
Нет: `venue_type` («Тип площадки»), `capacity_max` («Вместимость»),
`project_type` («Тип проекта»).

`GET /site/projects` принимает: `q, city, age_min, age_max, height_min, gender, sort`.
Нет: `category`, `performers_count`, `price_min` / `price_max`,
`date_from` / `date_to` («Дата съёмки»), `looking_for` («Кого ищем»).

`GET /site/agencies` принимает только `q, city, page, page_size` — сортировки нет вообще.

**Что нужно:** добавить недостающие параметры либо подтвердить, что фильтры
надо убрать из интерфейса. Сейчас они отрисованы, но ни на что не влияют.

## 🟡 Формы и тела запросов

### 8. Бронирование площадки принимает только дату

```
POST /site/venues/{id}/book   { "shoot_date": "2026-09-01" }
```

Модалка «Забронировать» (Figma 164:17700) содержит четыре поля:
название проекта · дата · **временной слот** · комментарий.

**Что нужно:** принимать `project_name`, `time_slot` (или `time_from`/`time_to`)
и `comment`. Сейчас три поля из четырёх заполняются впустую.

### 9. Регистрация компании: некуда положить имя представителя

`POST /auth/register/customer` с `customer_type: "company"` принимает
`company_name`, `first_name`, `last_name`. В макете «Знакомство» (85:5241) для
компании два поля: «Название компании» и «Имя представителя».

Сейчас имя представителя пишем в `first_name`. Если планируется отдельное поле
(`representative_name`, как у агентства) — скажите, поправим.

## 🟡 Ошибки

### 10. `VALIDATION_ERROR` возвращает англоязычные тексты Pydantic

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте правильность заполнения полей",
    "details": {
      "errors": [{
        "type": "value_error",
        "loc": ["body", "email"],
        "msg": "value is not a valid email address: The part after the @-sign is a special-use or reserved name that cannot be used with email.",
        "input": "performer@shootinghub.local"
      }]
    }
  }
}
```

Верхний `message` на русском — хорошо. Но `details.errors[].msg` — сырой текст
Pydantic на английском, показывать его пользователю под полем нельзя.

**Что нужно:** либо русские тексты в `msg`, либо более простая структура:

```json
"details": { "email": "Укажите корректный адрес почты" }
```

Мы поддерживаем оба формата, но сейчас под полями показать нечего.

## 🟢 Мелочи

### 11. Числа приходят строками с нулями

`area_m2: "60.00"`, `ceiling_height_m: "4.50"` — выводим как «60 м²» и «4,5 м»,
обрезая на фронте. Удобнее было бы получать числом.

### 12. `GET /site/chats` возвращает массив, остальные списки — объект

Все остальные списки — `{ items, meta }`, а чаты — просто `[]`. Не критично,
но единообразие упростило бы код.

### 13. Тестовые данные

Спасибо за наполненную базу — очень помогло. Две просьбы:
- у большинства исполнителей `logo_url` ведёт на `picsum.photos` (случайные
  пейзажи), из-за чего сложно проверять вёрстку карточек с портретами;
- у площадок и проектов почти везде одинаковые цены (`от 25 000 ₽`), не видно
  работы сортировки по цене.

## 🔴 Блокеры (добавлено 21.08.2026, после интеграции админки)

### 14. Нет доступа в админ-панель — весь раздел не проверен «вживую»

`POST /admin/auth/login` работает (отвечает `401 UNAUTHORIZED` на неверные данные),
но у нас нет ни одной учётной записи администратора. Подбирать пароль мы,
разумеется, не стали.

**Что нужно:** тестовый админ (email + пароль), желательно на стенде.

**Что это значит сейчас:** весь раздел `/admin/*` (дашборд, исполнители,
заказчики, агентства, проекты, площадки, модерация, жалобы, отзывы, чаты, FAQ,
контакты, документы) написан по Swagger-схемам и `backend/admin.md`, собирается
без ошибок, но **ни один экран не проверен на реальном ответе**. Как только
будет учётка — прогоним и пришлём список расхождений.

## 🟠 Схемы, из-за которых пришлось угадывать

### 15. У ответов админских `GET .../{id}` нет схемы в Swagger

```
GET /admin/performers/{user_id}   → "Response Get Performer ..."   (без полей)
GET /admin/customers/{user_id}    → "Response Get Customer ..."    (без полей)
GET /admin/agencies/{user_id}     → "Response Get Agency ..."      (без полей)
GET /admin/projects/{project_id}  → "Response Get Project ..."     (без полей)
GET /admin/venues/{venue_id}      → "Response Get Venue ..."       (без полей)
GET /admin/moderation/{source}/{entity_id} → тоже без полей
```

Тела запросов (`PerformerWriteRequest`, `CustomerWriteRequest`,
`AgencyWriteRequest`, `ProjectWriteRequest`, `VenueWriteRequest`) описаны
отлично — спасибо. А вот ответы — `Any`, поэтому форму карточки мы взяли
по аналогии с `GET /site/performers/{id}` (`{ user, profile, media, prices,
experience, reviews, stats }`).

**Что нужно:** `response_model` у этих шести ручек. Если структура отличается
от публичной — скажите, поправим адаптеры (`lib/adapters.js`).

### 16. «Сфера деятельности» заказчика некуда сохранить

В макете профиля компании (Figma 338:16487) есть поле «Сфера деятельности»
(например, «Российский бренд одежды»). В `CustomerWriteRequest` полей:

```
customer_type, first_name, last_name, company_name, city, email, phone,
password, about, website, contact_phone, inn, logo_url
```

— подходящего нет. У агентства такое поле есть (`sphere_of_activity`).

**Что нужно:** добавить `sphere_of_activity` (или `business_field`) в
`CustomerWriteRequest` и в ответ `GET /admin/customers/{id}`.
Пока поле в форме есть, но не отправляется.

## 🟡 Поведение, которое расходится с макетом

### 17. Агентство не может добавить исполнителя без email или телефона

```
POST /agency/performers
{ performer_specialty, first_name, last_name, city, ... }
→ 409 CONFLICT  "Укажите email или телефон"
```

В макете «Добавить исполнителя» (270:21262) полей входа нет вообще — агентство
заводит анкету модели, у которой своего кабинета может и не быть.

**Что мы сделали:** добавили в этот сценарий два поля («Электронная почта»,
«Телефон») — вне макета, иначе форма нерабочая.

**Вопрос:** так и задумано (у каждого исполнителя обязательно свой аккаунт),
или для анкет от агентства контакты стоит сделать необязательными? Если
задумано — оставим поля и попросим дизайнера их отрисовать.

### 18. Список приглашений и откликов — уточнение по именам ручек

Для протокола, чтобы не искали: мы сначала стучались в `/customer/responses`
и `/performer/invites` (по названиям экранов) и получали 404/405. Правильные:

```
GET /customer/applications                     — отклики на мои проекты
POST /customer/applications/{id}/accept|reject — решение по отклику
POST /customer/invites                         — пригласить исполнителя
GET  /performer/applications                   — мои отклики
```

Отдельного списка «Приглашения» у исполнителя нет — экран собираем из
`/performer/applications` и уведомлений. Если планируется отдельная ручка —
скажите, переключимся.

### 19. У агентства нет своего списка проектов

Экран `/agency/projects` («Проекты» в меню кабинета) должен показывать проекты,
в которых участвуют исполнители агентства. Подходящей ручки нет:
`/agency/*` даёт только `cabinet`, `performers`, `reviews`, `chats`.

**Что сейчас:** показываем общий каталог `GET /site/projects`.

**Что нужно:** `GET /agency/projects` (или `GET /agency/applications`) —
отклики/приглашения исполнителей агентства с их статусами.

### 20. `GET /performer/portfolio` отвечает 500

```
GET /api/v1/performer/portfolio
Authorization: Bearer <performer>
→ 500  { "code": "INTERNAL_ERROR", "message": "Внутренняя ошибка сервера" }
```

Воспроизводится с любыми параметрами и без них (`?page=1`, `?page_size=30`,
`?album=`). Соседние ручки того же раздела работают:

```
POST   /site/upload                  → 201 { url }
POST   /performer/portfolio          → 201 (медиа создаётся)
DELETE /performer/portfolio/{id}     → 200
GET    /performer/cabinet            → 200, в ответе есть media[]
```

**Что сейчас:** страница «Портфолио» (`/executor/portfolio`) берёт список из
`GET /performer/cabinet` → `media`. Как только ручка починится, вернём
`performerApi.portfolio()` — одна строка.

### 21. Нельзя отправить сообщение без текста, только с картинкой

`ChatMessageRequest`: `body` — `required`, `minLength: 1`.

```
POST /customer/chats/{id}/messages
{ "body": "", "attachment_url": "https://.../uploads/xxx.jpg" }
→ 422
```

В макете у чата есть скрепка (иконка `paperclip`), и обычный сценарий —
отправить фото без подписи.

**Что сейчас:** если пользователь ничего не написал, в `body` уходит имя файла
(«model.jpg»), чтобы пройти валидацию.

**Что нужно:** разрешить пустой `body`, когда есть `attachment_url`
(например `body: str | None` + проверка «хотя бы одно из двух непустое»).
